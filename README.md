# سفارش — Sefaresh MVP

دستیار خرید مواد اولیه برای کافه‌ها و رستوران‌ها؛ فارسی، راست‌به‌چپ و مناسب موبایل.

دموی محلی برای آزمون کاربردپذیری آماده است. [گزارش تحویل و نتایج آزمون‌ها](docs/QA.md) دامنه اجرا، شواهد و پیش‌نیازهای پایلوت واقعی را توضیح می‌دهد.

## اجرای سریع دمو

نیازمندی: **Node.js 22.18 یا بالاتر** و npm. برای آزمون‌های مرورگر، Chrome نصب باشد.

```powershell
npm ci
npm run dev
```

سپس **http://127.0.0.1:3000** را باز کنید. برای دموی محلی نیازی به کلید یا حساب Supabase نیست. فایل `.env.local` نسازید، یا دو مقدار Supabase را خالی بگذارید.

در صفحه ورود، دکمه‌های «ورود به‌عنوان مالک کسب‌وکار»، «مسئول خرید»، «کارمند»، «تأمین‌کننده» و «مدیر سامانه» حساب‌های آماده را باز می‌کنند؛ رمز ندارند. همچنین می‌توانید حساب آزمایشی دلخواه با ایمیل و رمز حداقل ۸ کاراکتری بسازید، کسب‌وکار خود را ثبت کنید و از ابتدا خرید انجام دهید. رمز واقعی خود را در دمو وارد نکنید.

داده دمو فقط در همان مرورگر و همان آدرس ذخیره می‌شود؛ `localhost` و `127.0.0.1` فضای ذخیره متفاوت دارند. هیچ پیام، خرید، پرداخت یا سفارش واقعی به تأمین‌کننده ارسال نمی‌شود. رمز حساب‌های آزمایشی با PBKDF2 و salt ذخیره می‌شود، اما این حالت مرز امنیتی تولید نیست؛ کاربران محلی به داده مرورگر دسترسی دارند.

## مسیر نمایش محصول

1. از `/register` حساب بسازید؛ در `/onboarding` نام، نوع، تماس و محدوده کسب‌وکار را ثبت کنید.
2. در داشبورد «ثبت درخواست جدید» را انتخاب کنید. مثال: ۳ کیلوگرم دانه قهوه، ۱۲ لیتر شیر، ۲ بطری سیروپ.
3. درخواست را بازبینی و در صورت نیاز ویرایش کنید. مقدار و واحد بر اساس واحد پایه کالا نمایش داده می‌شوند.
4. با نقش مالک/مدیر/مسئول خرید، درخواست را تأیید و به سبد اضافه کنید.
5. مقدار و یادداشت سبد را ذخیره کنید. وارد مقایسه شوید؛ معیار هزینه، سرعت یا تعداد تأمین‌کننده را انتخاب کنید.
6. «پیشنهاد سبد با این معیار» ترکیب قابل سفارش را پیشنهاد می‌کند؛ یا برای هر قلم تأمین‌کننده جدا انتخاب کنید.
7. اقلام، حداقل خرید، ارسال، مبلغ نهایی و زمان تقریبی را بازبینی کنید. نشانی را بنویسید و تیک تأیید را بزنید.
8. سفارش در داشبورد، سفارش‌ها و سابقه خرید ذخیره می‌شود. برای تغییر وضعیت در دمو از صفحه ورود به نقش مدیر سامانه بروید؛ تاریخچه، زمان، عامل و یادداشت نگهداری می‌شود.

برای آزمودن نبود پیشنهاد، مدیر سامانه یک کالای تازه بدون قیمت بسازد؛ آن را به سبد اضافه کنید. صفحه مقایسه مشکل را مشخص می‌کند و تا اصلاح/حذف قلم، ثبت سبد ناقص را نمی‌پذیرد.

## ساخت و اجرای تولید

```powershell
npm run build
npm run start
```

پورت پیش‌فرض ۳۰۰۰ است. قبل از `start`، سرور توسعه همان پورت را ببندید. برای پورت دیگر: `npm run start -- --port 3001`.

## اتصال Supabase

این بخش برای زمانی است که بخواهید از دموی محلی به داده واقعی بروید. اتصال زنده در این تحویل آزمایش نشده؛ کاربر اجرای محلی بدون کلید را انتخاب کرده است.

1. یک پروژه Supabase آزمایشی بسازید. ایمیل/رمز را در Authentication فعال کنید.
2. فایل‌های SQL زیر را به‌ترتیب در SQL Editor همان پروژه اجرا کنید:
   - `supabase/migrations/001_initial.sql`
   - `supabase/migrations/002_edit_requests.sql`
   - `supabase/migrations/003_business_updates.sql`
   - `supabase/seed.sql` برای ۱۰ دسته، ۱۲ کالا، ۴ تأمین‌کننده فرضی و ۴۸ پیشنهاد قیمت.
3. `.env.example` را به `.env.local` کپی کنید:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLIC_PUBLISHABLE_KEY
```

کلید قدیمی anon نیز از طریق `NEXT_PUBLIC_SUPABASE_ANON_KEY` پشتیبانی می‌شود. **هرگز service-role key را در متغیر `NEXT_PUBLIC_*` قرار ندهید.**

4. در تنظیمات Auth، Site URL را برای توسعه `http://127.0.0.1:3000` و برای استقرار دامنه واقعی بگذارید. در صورت فعال بودن تأیید ایمیل، کاربر ابتدا پیوند تأیید را باز می‌کند و سپس از صفحه ورود ادامه می‌دهد. برای ارسال قابل اتکا در پایلوت، SMTP خودتان را تنظیم کنید.
5. سرور را دوباره اجرا کنید؛ در حالت واقعی دکمه‌های ورود نمایشی حذف می‌شوند. داده محلی خودکار به Supabase منتقل نمی‌شود.
6. اولین حساب را ثبت کنید. برای اختصاص نقش مدیر سامانه، شناسه صحیح کاربر را از Auth بگیرید و فقط در SQL Editor اجرا کنید:

```sql
update public.profiles set role = 'admin' where id = 'ACTUAL_AUTH_USER_UUID';
```

برای حساب تأمین‌کننده، پس از ثبت‌نام، `role = 'supplier'` و `supplier_id` واقعی را با SQL Editor امن تعیین کنید. خود کاربر نمی‌تواند نقش سامانه را تغییر دهد. تأمین‌کننده فقط سفارش‌های متعلق به خود را می‌بیند و وضعیت آن‌ها را مرحله‌به‌مرحله تغییر می‌دهد.

**عضو تیم:** کاربر حساب بسازد و پیش از ساخت کسب‌وکار مستقل، مدیر سامانه او را در `/admin/customers` به کسب‌وکار موجود اضافه کند. هر حساب در MVP عضو یک کسب‌وکار است. مالک می‌تواند نقش اعضای موجود را تغییر دهد؛ افزودن عضو جدید توسط مدیر سامانه انجام می‌شود.

## امنیت و پایگاه داده

۱۵ جدول با UUID، کلید خارجی، محدودیت عددی، شاخص و RLS:

`profiles`, `businesses`, `business_members`, `categories`, `products`, `suppliers`, `supplier_products`, `supplier_offers`, `material_requests`, `material_request_items`, `procurement_baskets`, `basket_items`, `orders`, `order_items`, `order_status_history`.

- داده خصوصی کسب‌وکار به عضویت و نقش محدود است؛ کارمند درخواست‌های خود را می‌بیند.
- مدیر سامانه عملیات کالا، دسته‌بندی، تأمین‌کننده و قیمت را انجام می‌دهد.
- ثبت‌نام نمی‌تواند نقش admin/supplier را از metadata دریافت کند.
- نقش‌های مالک، مدیر، خریدار، کارمند، تأمین‌کننده و مدیر سامانه تعریف شده‌اند.
- تغییرات حساس از RPCهای اتمیک انجام می‌شوند؛ نوشتن مستقیم در سفارش‌ها، سبد و عضویت‌ها مجاز نیست.
- checkout قیمت و زمان تغییر، نسخه سبد، موجودی، واحد، اندازه بسته، حداقل مقدار و حداقل خرید را دوباره بررسی می‌کند. هر تأمین‌کننده یک هزینه ارسال دارد: بیشترین هزینه پایه یا هزینه عرضه اقلام او.
- ثبت مجدد همان شناسه checkout، سفارش تکراری نمی‌سازد. کل ثبت چند سفارش در یک تراکنش انجام می‌شود.
- وضعیت‌ها ترتیبی‌اند؛ همه تغییرات سفارش دارای زمان، عامل و یادداشت هستند. لغو پس از ارسال/تحویل مجاز نیست؛ لغو یادداشت می‌خواهد.
- اطلاعات نشانی، قیمت و مشخصات سفارش snapshot است؛ تغییر بعدی فهرست کالا سفارش گذشته را تغییر نمی‌دهد.
- Proxy جلسه Supabase را بررسی می‌کند؛ RLS و مجوز RPCها مرز نهایی دسترسی‌اند.

## آزمون‌ها

```powershell
npm run typecheck
npm run lint
npm test
npm run test:db
npm run build
npm run test:e2e
```

- Vitest: منطق قیمت، ارسال، حداقل خرید، بسته‌بندی، پیشنهاد سبد، درخواست و سفارش، جلوگیری از تکرار و قیمت قدیمی.
- PGlite/PostgreSQL: اجرای خود migrationها و seed، دو کسب‌وکار مستقل، RLS و نقش‌ها، RPCها و تراکنش checkout. به پروژه Supabase یا Docker نیاز ندارد. شبیه‌ساز schema احراز هویت فقط در محیط آزمون ساخته می‌شود.
- Playwright: ثبت‌نام تا تاریخچه، ویرایش چند قلم، پیشنهاد و انتخاب دستی تأمین، ورود دوباره، مدیریت قیمت/وضعیت، نبود پیشنهاد، مجوزها و اندازه دسکتاپ/موبایل. ابتدا `npm run build` را اجرا کنید؛ آزمون سرور production را خودش روشن و پس از پایان خاموش می‌کند. پیش‌فرض از Chrome نصب‌شده استفاده می‌کند؛ یا Chromium را با `npx playwright install chromium` نصب کنید و `PLAYWRIGHT_CHANNEL=chromium` بگذارید.
- گزارش مرورگر در `playwright-report` و تصاویر بازبینی در `tmp/qa` ساخته می‌شوند.

## معماری و پوشه‌ها

Next.js 16 App Router، React، TypeScript، Tailwind CSS 4 و CSS با توکن‌های برند، Zod، Supabase JS/SSR، Vazirmatn محلی و آیکون‌های خطی Lucide.

```text
src/app/                مسیرها، layout، خطا، 404 و سبک برند
src/components/         فرم‌ها، پوسته، داشبورد و صفحات عملیاتی
src/lib/types.ts        انواع داده
src/lib/domain.ts       مقایسه و پیشنهاد سبد
src/lib/demo.ts         اجرای همان عملیات در دموی محلی
src/lib/seed.ts         داده نمونه
src/lib/supabase.ts     اتصال عمومی Supabase
src/proxy.ts            کنترل جلسه مسیرهای محافظت‌شده
supabase/migrations/    schema، مجوزها و توابع
supabase/seed.sql       کاتالوگ و پیشنهادهای فرضی
tests/unit/             آزمون‌های منطق
tests/e2e/              آزمون‌های مرورگر
scripts/                بررسی پایگاه داده و تولید seed
public/rosha.png         تصویر اصلی و بدون تغییر روشا
```

مسیرها: `/`, `/login`, `/register`, `/onboarding`؛ `/app`؛ `/app/requests`, `/app/requests/new`, `/app/requests/[id]`, `/app/requests/[id]/edit`؛ `/app/products`, `/app/cart`, `/app/compare`, `/app/orders`, `/app/orders/[id]`, `/app/history`, `/app/suppliers`, `/app/profile`؛ و `/admin`، `/admin/products`, `/admin/suppliers`, `/admin/offers`, `/admin/requests`, `/admin/orders`, `/admin/orders/[id]`, `/admin/customers`.

فقط سه تصویر تأییدشده کاربر منبع بصری‌اند؛ نام و جزئیات آن‌ها در `docs/IMPLEMENTATION.md` ثبت شده است. رنگ‌ها و فونت از تصویر کیت برند، فرم‌ها و کارت‌ها از تصویر کاربردها و روشا از PNG اصلی استفاده می‌شوند. تصویرسازی تصادفی یا بازطراحی کاراکتر اضافه نشده است.

## محدودیت‌های نسخه اولیه

- قیمت‌ها و تأمین‌کنندگان seed فرضی‌اند؛ هیچ صرفه‌جویی یا زمان تحویل واقعی تضمین نمی‌شود.
- حالت محلی چندکاربره واقعی یا همگام‌سازی بین دستگاه‌ها ندارد. مرورگر محل نگهداری همه داده دمو است؛ پاک کردن داده سایت آن را حذف می‌کند.
- جست‌وجوی ترکیب تأمین به ۲۰۰٬۰۰۰ گره محدود است؛ در سبدهای بزرگ، بهترین گزینه میان ترکیب‌های بررسی‌شده پیشنهاد می‌شود و پیام عدم قطعیت نمایش داده می‌شود.
- واحد پایه کالا ثابت است و تبدیل واحد/جایگزینی برند انجام نمی‌شود. مقدار هر سطر باید با بسته‌بندی و حداقل مقدار عرضه سازگار باشد.
- انتخاب تاریخ فیلتر با ورودی بومی میلادی است؛ تاریخ‌های نمایش داده‌شده شمسی‌اند.
- مدیریت قیمت دستی است؛ پرداخت، ارسال پیام به تأمین‌کننده، لجستیک، انبارداری، حسابداری، recipe costing و پیش‌بینی تقاضا خارج از MVP هستند.
- دعوت ایمیلی و پنل ویرایش قیمت توسط تأمین‌کننده در این نسخه نیست؛ مدیر سامانه آن‌ها را اداره می‌کند.

## پنج گام بعدی

1. اتصال یک پروژه آزمایشی Supabase و آزمون تأیید ایمیل و SMTP روی دامنه واقعی.
2. جایگزینی تأمین‌کنندگان و قیمت‌های فرضی با داده تأییدشده محلی کرمان.
3. اجرای پایلوت با ۱۰ تا ۲۰ کافه و ثبت زمان خرید، خطاهای اصلاح‌شده و خرید مجدد.
4. تکمیل دعوت اعضای تیم و اعلان وضعیت سفارش بر اساس بازخورد پایلوت.
5. تعریف فرایند تأیید موجودی، رسیدگی به تأخیر/مغایرت و سپس آزمون بار و پشتیبان‌گیری پیش از عرضه عمومی.
